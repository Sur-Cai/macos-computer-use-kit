# Jev / TypeSafe System One 最佳实践（沉淀）

来源：TypeSafe 官方文档 + 社区实践（ArchCrux、flaviocopes、systemonemodels、Bloss0m、apidog、volanea 等，2026-09）。

## 定位：决策层，不是工作流

```
LLM 生成 ｜ Jev 判断 ｜ 代码控制 ｜ 人处理边缘
```
Jev 只回答**有限选项内的窄判断**，返回类型化答案 + 校准概率。它不写文本、不做多跳推理。
控制流与副作用永远留在代码里。

## 问题设计（Question design）

1. **一问一判断**。"这个线索有价值、紧急、且可能成交吗？"是三个问题，拆开再在代码里组合权重。
2. **原语匹配判断形状**：
   - 有梯度的（严重度、质量、匹配度）→ `score`（2–10 级）
   - 单一事实判断 → `noul`
   - 固定选项集 → `choice`（最多 255 个选项，超过要两段式）
3. **描述情境，不描述程度**：Score 的每一级要写"具体是什么状态"（"功能坏了但有绕过方案"），
   而不是"中等严重"。选项之间要写清边界差异。
4. **必须给逃生口**：`other` / `none_of_the_above` / `unknown` / `not_stated` / `needs_human_review`。
   选项集覆盖不到时，模型只能选错的。
5. **instructions 与 criteria 说同一件事**，用同事一眼能懂的话；两者矛盾会掉分。
6. **不要让模型解释自己**：回答里只有决策、概率、置信度。

## 状态（State）

- **只放判断需要的**。无关内容会显著降准（context rot）；能确定性过滤就先过滤，
  不能就用 Noul 逐块判"是否相关"再丢掉。
- 请求上限 64K tokens，其中 state + 最长问题 ≤ 32K。
- 用户可控内容视为**不可信输入**（提示注入），不要让它影响系统权限与策略。

## 并行（Speculative fan-out）

- 所有**互相独立**的问题放进**同一次调用**（官方 cookbook：13 个问题批量 = 12.2x 便宜、10x 快）。
- 只有"下一个问题依赖上一个答案"（需要先取数据/先确定选项集）时才发第二次请求。
- 代价：会为可能用不到的判断付费；记录时要区分 unused / rejected / policy-conflict。

## 置信度与策略（Confidence & policy）

- **置信度是模型信号，不是授权**。身份、权限、资源范围、审批必须由运行时校验。
- 按**做错的代价**设阈值：只读/可逆 → 可低；可恢复的外部动作 → 高；不可逆/敏感 → 必须人工。
- 起始参考（要用自己的数据校准）：>0.85 自动执行；0.55–0.85 交给更强模型/二次判断；<0.55 给人。
- 保留**原始维度 + 权重版本 + 最终路由**，不要只留一个合成分数。

## 运维（Operations）

- **固定模型版本**：`jev-latest` 会漂移；自动化路径用 `jev-1.13.0` 这类具体版本。
- 版本化：问题、阈值、决策 schema 各自独立版本号。
- 记录：state 快照、问题版本、模型版本、概率、策略版本、最终结果 → 才能回溯与校准。
- 用带标签的真实样本测：混淆矩阵之外还要看 coverage–risk 曲线、升级率、p95 延迟、每成功任务成本。
- 失败分类：schema 失败 / 语义失败 / 校准失败 / 策略失败（分别处理）。

## 不要用 Jev 的地方

算术、精确计数、日期计算、多跳推理、需要生成文本、需要读图、以及**普通代码已经能正确判断**的一切。
（一个免费的 `if` 胜过千分之一美元且可能出错的 `if`。）
